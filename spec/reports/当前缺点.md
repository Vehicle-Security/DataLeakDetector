## **合理性**

比如：

`file_selected browser_file_access created zip clipboard_copy screen_share_start`

这些都只能说明：

`准备 / 尝试 / 可疑 / 暴露风险`

不能说明：

`成功外泄`

所以合理架构应该是：

`日志规则 -> suspected / attempted / staging 关键帧 + OCR/VLM -> submitted / content_exposed / completed Datalog -> 把对象传播链和成功证据串起来`

也就是说，日志可以触发告警或进入复核，但不应该轻易作为“成功泄露”的最终证据。

我觉得当前项目应该把判定层拆清楚：

| 层级                          | 可由日志判断吗 | 需要 VLM 吗                |
| ----------------------------- | -------------- | -------------------------- |
| 敏感文件被使用                | 可以           | 不一定                     |
| 敏感文件被派生/压缩/改名      | 可以           | 不一定                     |
| 文件进入上传/附件流程         | 可以           | 不一定                     |
| 用户点击发送/上传             | 部分可以       | 经常需要                   |
| 界面显示发送/上传成功         | 很难           | 需要                       |
| 敏感内容在 AI/聊天/会议中可见 | 很难           | 需要                       |
| 成功外泄确认                  | 不应只靠日志   | 通常需要视觉/网络/远端证据 |

所以“纯日志直接 final positive”最好改成：

`log_positive -> risk_positive / staging_positive visual_positive -> submitted_or_completed datalog_confirmed -> confirmed_leak`

换句话说：

**日志可以说“值得查”，VLM 才应该负责把“值得查”升级成“确实发生了”。**

当前项目的问题不是用了日志，而是日志/规则和 VLM 输出的证据强度没有严格区分，导致：

`file_selected / upload_start / selected_or_attached`

这类准备态被一路推到了 final positive。
你现在抓到的正是系统最该修的语义边界。

我觉得要分开说：

**架构方向没大问题，但当前判定方案有问题。**

架构本身其实是合理的：

```text
日志定位可疑时间段
关键帧/OCR/VLM 理解画面语义
EventCorrelator 绑定文件、应用、时间、窗口
Datalog 拼接证据链
输出风险报告
```

这和 `要求.md` 的方向是一致的：日志不是终点，而是定位和增强证据；VLM 用来判断复杂 UI 和成功状态；Datalog 负责解释链路。

真正有问题的是当前实现里的**证据强度分层**和**最终判定口径**。

现在的问题大概有三类：

1. **把尝试/准备态推得太靠近最终正例**
   例如：

   ```text
   file_selected
   attach_file
   upload_start
   selected_or_attached
   in_progress
   remote listing visible
   ```

   这些不应该直接等价于成功外泄。
2. **Datalog 里 LeakFile 生成过宽**
   只要 action_type / risk_level 到某些条件，就可能生成 `LeakFile`。但 `LeakFile` 语义应该更严格，最好只表示：

   ```text
   submitted / completed / content visibly exposed to external party
   ```

   而不是普通 staging。
3. **VLM 输出和后处理存在矛盾仍被采信**
   你刚才看到的 FP 里，有些描述写着：

   ```text
   not sent yet
   no visual confirmation
   no sensitive file exposed
   ```

   但 action 又被抽成 `send_message completed`，最后 Datalog 仍然推成泄露。这说明 action parser / fusion 层缺少一致性校验。

所以不是说整个架构错了，而是应该改成更严格的分层架构：

```text
Log Rules:
  sensitive_use
  derived_artifact
  staging
  attempted_transfer

VLM/OCR:
  selected_or_attached
  content_exposed
  submitted
  completed
  negative / inbound / draft / cancelled

Datalog:
  只把 submitted/completed/content_exposed 这类强证据转成 LeakFile
  staging 只能生成 TransferFile 或 RiskSupport，不能生成 confirmed leak

Final:
  risk_positive = staging 或 attempted
  confirmed_leak = submitted/completed/content_exposed + sensitive object binding
```

这样架构就不会偏。

更直白地说：

**问题不是“用了日志规则”，而是日志规则和 VLM 证据没有被严格区分成风险等级。**
日志规则可以保留，而且很有用；但它应该更多用于“定位和预警”，不是直接替代“成功外泄确认”。

如果你现在要调整项目方向，我会建议优先做这几件事：

1. **重命名/重定义 final**
   当前 final 更像 `risk_positive`，不要叫泄露成功。
2. **收紧 `LeakFile` 生成条件**
   `attach_file`、`upload_start`、`selected_or_attached`、`in_progress` 不直接生成 `LeakFile`。
3. **增加 `SubmittedFile` / `ExposedContent` / `CompletedTransfer` 中间事实**
   Datalog 不要只有 `LeakFile` 一种终点。
4. **VLM 输出加一致性检查**
   如果 description 里有 `not sent yet / no confirmation / no sensitive file exposed / draft / save as / inbox`，就不能升级成 completed。
5. **单独评估 confirmed_leak**
   不要只看 final F1，要看“成功外泄确认”指标。

所以我的判断是：

```text
架构：基本对
当前方案口径：有明显问题
当前指标：更像风险识别指标，不应被解释成成功泄露确认指标
```

这也是为什么你会觉得它和“关键帧 + VLM 补全证据链”的目标有冲突：不是模块不该这样排，而是证据层级没有守住。

## 鲁棒性

这条链路的上限，主要卡在“事实供给是否稳定”，不是 Datalog 本身。

1. `敏感对象绑定` 仍然偏脆
   当前很多后续事实都建立在先拿到 `sensitive_files`、再把 action 里的 `source_file/derived_file` 对上这个集合。核心入口在 [benchmark_nas_samples.py](/d:/Projects/Job/DataLeakDetector/tools/benchmark_nas_samples.py:3888) 和 [benchmark_nas_samples.py](/d:/Projects/Job/DataLeakDetector/tools/benchmark_nas_samples.py:4411)。问题是，一旦敏感对象没有在日志、窗口标题、文件名、VLM 描述里被稳定提取出来，后面根本不会生成足够强的事实。这个对“内容外泄但文件名不明显”的场景尤其脆。
2. `CrossProcessTransfer` 能力在新链路里没有真正吃满
   Datalog 规则本体是支持 `CrossProcessTransfer / ClipboardWrite / ClipboardRead` 的，见 [taint_rules.dl](/d:/Projects/Job/DataLeakDetector/03-LeakReasoner/datalog/taint_rules.dl:1) 和 [python_datalog_engine.py](/d:/Projects/Job/DataLeakDetector/03-LeakReasoner/datalog/python_datalog_engine.py:1)。但新 benchmark 的 audit-action 转事实链里，几乎主要还是 `OpenFile / TransferFile / LeakFile`，我前面查过 `tools/benchmark_nas_samples.py` 并没有实际注入 `CrossProcessTransfer` 那几个关系。这意味着规则“理论上能推”，但现实里事实没喂进去，跨进程中转的鲁棒性就打折。
3. 关键帧选择是“强启发式”，不是稳定语义定位
   现在的 review window 和 segment 选择比纯平均抽帧强很多，见：

- [suspicious_window_builder.py](/d:/Projects/Job/DataLeakDetector/01-FrameAnalyzer/risk_hunter/suspicious_window_builder.py:208)
- [benchmark_nas_samples.py](/d:/Projects/Job/DataLeakDetector/tools/benchmark_nas_samples.py:962)
- [benchmark_nas_samples.py](/d:/Projects/Job/DataLeakDetector/tools/benchmark_nas_samples.py:1457)

但它依然很依赖：

- token
- candidate events
- 已知上下文词
- 敏感锚点附近时间窗

所以换个 UI、换个提示文案、换个产品名，或者根本没有明显“上传成功/发送/附件”文本时，关键帧可能截不到最有用证据。

4. VLM 对“显式完成态”较强，对“边界态”不够稳
   多 segment 合并逻辑在 [benchmark_nas_samples.py](/d:/Projects/Job/DataLeakDetector/tools/benchmark_nas_samples.py:2982)。
   它的优点是有上下文，不是单帧乱猜。
   但风险是：只要出现高置信正段，就会把 case 往正向推。这对 recall 有帮助，但对 precision 不够稳，尤其是：

- 已选择但未提交
- 云端列表可见但不是外发
- 普通文件上传误绑定成敏感文件
- 草稿/取消/未完成状态

5. EventCorrelator 是加分项，但还不是兜底项
   [run_e2e.py](/d:/Projects/Job/DataLeakDetector/main/run_e2e.py:2104) 里的 EventCorrelator 会补：

- upload_candidates
- file_lineage
- operation_records

这对显式文件外发有帮助。
但它仍然依赖已有日志和帧段质量，不能从根上修复“敏感对象绑定错了”或“关键证据帧没截到”的问题。

**结论清单**

**当前相对鲁棒的部分**

- 显式文件上传完成
- 明确发送完成
- 共享屏幕开始
- 截图/录屏
- VM/远程桌面这类高语义场景
- 有明确文件谱系的改名/导出/压缩后外发

**当前不够鲁棒的部分**

- 剪贴板中转
- 跨进程传播
- 内容外泄但文件名不明显
- 普通文件与敏感文件的误绑定
- 云端编辑/远端列表/附件草稿等边界态
- 新应用、新 UI、新提示文案
- 没有明显完成提示词的泄露行为

**最该补的 3 件事**

1. 补强事实层的跨进程传播
   目标：把 `ClipboardWrite / ClipboardRead / CrossProcessTransfer` 真正接到新 audit-action -> datalog 链路里。原因：这是现在“理论支持但实际上没充分喂事实”的最大短板。优先级：最高。
2. 补强敏感对象绑定，而不是只补渠道识别
   目标：

- 把“上传了什么”“展示了什么”“复制了什么”与敏感源对象更稳地关联
- 降低“普通文件上传被误认成敏感文件上传”的概率
  原因：现在很多误报不是因为看不懂“在上传”，而是因为“绑定错了对象”。
  优先级：最高。

3. 补强关键帧和 segment 选择的语义覆盖
   目标：

- 除了 token 和候选事件，再增加更稳定的视觉锚点
- 特别是未完成上传、云端列表、远端编辑器、附件草稿这些边界态
  原因：VLM 再强，没看到关键证据也白搭。
  优先级：高。

**如果你现在要一个实际行动顺序**

1. 先补 `CrossProcessTransfer` 事实注入
2. 再补敏感对象绑定
3. 再调关键帧策略
4. 最后再细调 VLM prompt / postprocess

## 可维护性

**现在的代码比较丑陋**。不是“不能用”的那种丑，而是典型的“为了把实验跑通、把指标顶上去，逻辑不断堆在 benchmark 脚本里”的丑。

我刚扫了一下核心文件，几个信号很明显：

```text
tools/benchmark_nas_samples.py   4912 行，130 个函数/类
main/run_e2e.py                  2432 行，39 个函数/类
tools/log_signal_rules.py         374 行，但核心函数 247 行
```

最丑的点主要是这些：

1. **benchmark 脚本承载了太多生产逻辑**
   `benchmark_nas_samples.py` 里同时有：

   - 数据集读取
   - 日志清洗
   - VLM gate
   - 抽帧
   - OCR
   - VLM prompt
   - VLM 后处理
   - EventCorrelator 调用
   - audit actions
   - Datalog fact 生成
   - metric 统计
   - replay 逻辑

   这已经不是 benchmark script，更像一个巨型实验操作台。
2. **证据语义混在一起**
   `selected_or_attached`、`in_progress`、`content_exposed`、`completed`、`LeakFile`、`risk_support` 这些层级没有被干净建模，所以才会出现“没成功也推成正例”的问题。
3. **很多逻辑是为当前数据集补丁式调出来的**
   `record.md` 里也写了“预言机分析”“全数据集零误报规则”。这对冲指标有效，但代码会越来越像 benchmark rulebook，而不是通用检测系统。
4. **函数太长，职责边界不清**
   比如：

   - `run_benchmark` 449 行
   - `_live_vlm_review_case` 189 行
   - `_audit_action_supports_risk` 149 行
   - `_audit_actions_to_datalog_facts` 125 行
   - `extract_deterministic_signals` 247 行

   这些都已经到了“读的人很难确信改一处不会炸另一处”的程度。
5. **E2E、benchmark、真实模块之间有重复和倒挂**
   正常应该是：

   ```text
   core modules -> benchmark 调用 core
   ```

   但现在很多核心策略直接长在 `tools/benchmark_nas_samples.py` 里，反而 benchmark 成了事实上的主实现。
6. **历史包袱比较重**
   目录名、字段名、module3/module4、RiskHunter、fallback、ThreatDetector 这些历史概念还混在一起。能理解为什么会这样，但可维护性确实受影响。

所以我的判断是：

```text
架构想法：还可以
当前代码组织：偏丑
当前判定逻辑：补丁多，语义层不干净
当前指标：有实验价值，但不能直接代表工程质量
```

如果要收拾，优先级我会这么排：

1. 先把证据语义模型抽出来 `Staging / Attempted / Submitted / Completed / ContentExposed / ConfirmedLeak`
2. 把 `LeakFile` 生成条件收紧不要让 selected/in_progress 直接变 confirmed。
3. 从 `benchmark_nas_samples.py` 里拆核心模块至少拆成：

   - `visual_review/`
   - `evidence_fusion/`
   - `datalog_fact_builder/`
   - `benchmark_runner/`
4. benchmark 只负责跑数据和算指标不再承载核心算法。
5. 再做 visual-critical slice 和消融实验
   否则重构完还是不知道 VLM 真贡献了多少。

一句话：**现在代码是实验冲刺型代码，不是干净的产品型代码。能跑、能出指标，但已经到了该整理语义和模块边界的时候。**

## 算法偏重

**当前规则越来越擅长处理数据集里可枚举的日志模式，但 VLM 对复杂 UI、跨应用、远程/VM、会议共享、AI 输入框、内容暴露这些难场景的贡献没有被充分单独衡量和放大。**

更直接说：
当前项目不是“不依赖 VLM”，而是 **没有足够证明 VLM 正在解决规则解决不了的问题** 。

我会建议接下来把工程目标拆成三条，不然很容易继续被 benchmark 分数牵着走：

1. **建立 VLM-only / rules-only / rules+VLM 消融评测**
   看 VLM 独立新增了多少 TP，尤其在 stage2、stage4、stage5、AI、会议、VM、OCR 内容场景里。
2. **把关键帧检测作为独立模块评估**
   不只看最终 F1，而是看关键 UI 状态是否被抽到：

   * 发送成功帧 recall
   * 上传完成帧 recall
   * 敏感内容可见帧 recall
   * AI 输入框粘贴帧 recall
   * 会议共享敏感画面 recall
3. **把规则命中样本和视觉必要样本分层**
   简单日志强证据样本让规则处理没问题；但复杂样本必须要求：

   `日志只能定位窗口 关键帧必须捕获 UI 状态 VLM 必须输出可绑定 action Datalog 才能最终收束`
