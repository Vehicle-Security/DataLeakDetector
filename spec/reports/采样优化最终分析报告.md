## 执行摘要

**结论**: 采样策略优化对减少 FN（漏报）的效果**极其有限**（FN 从 62 → 61，仅减少 1 个）。

**根本原因**: 
1. ❌ **日志中没有完成事件** - 整个"完成事件密集采样"优化基于错误假设
2. ⚠️ **Ground Truth 标注质量存疑** - 很多 FN 案例可能本就不是"已完成"
3. ⚠️ **VLM 判断过于保守** - 缺少明确完成证据时，倾向于判断为"准备阶段"

## 关键发现

### 发现 1: 日志中没有完成事件 ⭐⭐⭐⭐⭐

**实际日志事件类型**（以 `stage1\1-email-163email-2` 为例）:
```
3775  browser_file_access
 165  modified
  84  created
  78  deleted
  42  opened
  42  renamed
   9  app_switch
   1  clipboard_text
```

**完全不存在的事件**:
- ❌ `upload_complete`
- ❌ `send_message`
- ❌ `message_sent`
- ❌ `upload_success`
- ❌ `commit_success`

**影响**:

我们的"完成事件密集采样"优化代码是这样的：

```python
# _event_anchor_times() 函数
is_completion = event_type in {
    "upload_complete", "send_message", "message_sent", "upload_success",
    "commit_success", "push_success", "publish_success"
}
if is_completion:
    # Dense sampling around completion moment
    offsets = (-5, -3, -1, 0, 1, 3, 5, 8, 12, 18, 25, 35)
    reason = f"completion_anchor_transfer:{event_type}"
```

**但这些事件在原始日志中根本不存在！** 所以：
- `is_completion` 永远是 `False`
- 密集采样的逻辑永远不会触发
- `completion_anchor` 不是通过完成事件创建的

### 发现 2: completion_anchor 实际上是 VLM 推断的

`upload_complete` 和 `send_message` 事件是由 **VLM 观察视频帧后推断**出来的：

```python
# _postprocess_vlm_actions() 函数
completion_patterns = {
    "upload": ["上传完成", "upload complete", "上传成功", "successfully uploaded"],
    "send": ["发送成功", "message sent", "已发送", "sent successfully"],
    "publish": ["发布成功", "published", "已发布"],
}

for action_category, markers in completion_patterns.items():
    if any(marker in description for marker in markers):
        if action_category == "upload":
            detected_type = "upload_complete"
        elif action_category == "send":
            detected_type = "send_message"
```

这是一个**循环依赖**：
1. 我们想在"完成事件"附近密集采样
2. 但"完成事件"本身是 VLM 看了帧之后推断出来的
3. 也就是说，我们需要先看到"完成证据"才能生成"完成事件"
4. 但我们正是为了看到"完成证据"才想密集采样

### 发现 3: 窗口扩展有轻微效果

**窗口扩展逻辑**:

```python
def _extend_segments_for_completion(segments, logs, fallback_meta):
    # 检测准备动作（file_selected, attach_file, upload_start）
    prep_events = find_events(logs, ['file_selected', 'browser_file_access', 'attach_file'])
    
    if prep_events:
        last_prep_time = max(prep_events)
        # 扩展窗口：最后准备动作 + 30 秒
        min_end_time = last_prep_time + timedelta(seconds=30)
        if segment_end < min_end_time:
            segment_end = min_end_time  # 延长窗口
```

**效果**:
- `completion_anchor` 覆盖从 64 → 69（+5 案例）
- 说明窗口扩展确实让一些案例看到了更多的"后续帧"

**但为什么 FN 只减少 1 个？**

可能的原因：
1. 扩展的 30 秒内，可能没有"发送成功"的明确证据
2. 有些案例本来就是"准备但未完成"（Ground Truth 标注错误）
3. VLM 即使看到了更多帧，也没有足够的完成证据来判断

2. 或者，用户只是打开了撰写窗口，最终没有发送（Ground Truth 标注错误）

### 案例 2: `stage5\VMware-openEuler`

**Ground Truth**: 已确认泄露  
**VLM 判断**: 准备阶段（selected_or_attached）

- VLM 明确看到了"附加"但没看到"发送"

### 案例 3: `stage4\7-2`

**Ground Truth**: 已确认泄露  
**VLM 判断**: 本地准备，非泄露

- 有剪贴板复制事件
- 但 VLM **没有看到粘贴到 Gemini 的帧**

**可能的原因**:

2. 粘贴时 Gemini 窗口被遮挡或最小化
3. 实际上内容没有粘贴到 Gemini（Ground Truth 错误）

## 为什么优化效果有限

### 1. **准备动作检测的局限性** ⚠️

窗口扩展依赖于检测 `file_selected`, `attach_file` 等事件：

```python
prep_events = find_events(logs, ['file_selected', 'browser_file_access', 'attach_file'])
```

但实际日志中：
- `file_selected` - **不存在**
- `attach_file` - **不存在**
- `browser_file_access` - **存在**，但是文件选择器打开的通用事件，无法区分是"选择上传"还是"选择下载"

所以，窗口扩展可能只在部分案例中生效（有 `browser_file_access` 的案例）。

### 2. **完成证据本质上很难捕捉** ⚠️⚠️

"发送成功"、"上传完成"的 UI 证据通常：
- **显示时间极短**（1-3 秒的 Toast 通知）
- **位置不固定**（可能在屏幕角落）
- **可能被遮挡**（其他窗口、通知）
- **可能不存在**（用户关闭了通知，或应用没有成功提示）

即使窗口延长 30 秒，如果关键的 1-2 秒没有被采样到，仍然会漏掉。

### 3. **采样密度的权衡** ⚠️⚠️⚠️

当前采样策略：
- 每个 segment: 45 秒
- 采样帧数: 8-12 帧
- 平均采样间隔: **4-6 秒**

如果"发送成功" Toast 只显示 2 秒：
- **被采样到的概率约 33-50%**

要提高到 90% 以上，需要：
- 采样间隔缩短到 1 秒
- 每个 segment 需要 45 帧
- 4 个 segments 需要 180 帧 → **成本暴增 15 倍**

### 4. **Ground Truth 标注质量存疑** ⚠️⚠️⚠️⚠️

从 VLM 的判断来看，很多 FN 案例的理由非常充分：

| 案例 | VLM 判断 | 理由 |
|-----|---------|-----|
| VMware-openEuler | 准备阶段 | 文件已附加，但发送按钮未点击 |
| U4-Bluetooth-2 | 进行中 | 蓝牙界面显示 "Connecting..."，无完成证据 |
| stage4\7-2 | 本地准备 | 无外部传输的视觉证据 |

这些判断**非常合理**。如果 VLM 是对的，那么问题在于 **Ground Truth 标注不准确**：
- 标注者可能看到了"准备动作"就标为"已完成"
- 或者标注的时间点不准确（标注了点击"发送"的时间，而非实际完成的时间）
- 或者有些案例确实"未完成"，但被误标为"已完成"

## 优化的真实效果

### 实际起作用的优化

#### ✅ 窗口扩展（轻微效果）

- **实现**: 检测到 `browser_file_access` 后，窗口延长 30 秒
- **效果**: `completion_anchor` 覆盖 +5 案例
- **贡献**: FN 减少 1 个（约 1.6%）

#### ❌ 完成事件密集采样（无效）

- **实现**: 在 `upload_complete`、`send_message` 事件前后密集采样
- **效果**: **完全无效**
- **原因**: 这些事件不存在于原始日志中

#### ⚠️ VLM Prompt 优化（难以评估）

- **实现**: 增强 Prompt，要求检测持久状态证据
- **效果**: 难以单独评估（与采样策略混合测试）
- **问题**: 即使 Prompt 再详细，如果采样的帧本身没有证据，VLM 也无法"凭空"看到

### 优先级 2: 混合决策策略（日志 + VLM） 🔧🔧🔧

**思路**: 不完全依赖 VLM，结合日志证据

```python
def hybrid_completion_decision(vlm_verdict, logs):
    vlm_risk = vlm_verdict['risk_level']  # selected_or_attached, in_progress, etc.
    
    # VLM 判断为准备或进行中
    if vlm_risk in {'selected_or_attached', 'in_progress'}:
        # 但日志有强证据
        strong_signals = [
            'browser_file_access' in后续10秒内消失（窗口关闭）,
            clipboard复制后，外部应用活跃,
            文件修改时间在准备动作之后（说明操作完成了）,
        ]
        
        if any(strong_signals):
            # 升级为完成
            return 'completed'
    
    return vlm_risk
```

**优点**:
- 利用日志的时间序列信息
- 弥补 VLM 采样间隙的盲区

**缺点**:
- 可能增加 FP（误判本地操作为泄露）

### 优先级 3: 极限密集采样（仅用于验证） 💰💰💰

**目标**: 验证"采样密度"是否是瓶颈

- FN 没有减少 → 说明问题不在采样密度，而在 Ground Truth 或完成证据本身不存在

### 优先级 4: 重新标注 Ground Truth 📊📊📊📊

**如果优先级 1 验证发现大量标注错误**，则需要：

1. **人工审查所有 FN 案例**:
   - 使用帧调试图片
   - 标注者重新判断是否"真的已完成"

2. **修正 Ground Truth**:
   - 将"准备但未完成"的案例标注修改为 `expected: false`
   - 或者添加新字段 `expected_level: attempted`（尝试但未完成）

3. **重新测试**:
   - 使用修正后的 Ground Truth
   - 重新评估 FN/FP 指标

## 结论

### 采样优化的效果

| 优化项 | 实际效果 | 原因 |
|-------|---------|-----|
| **窗口扩展** | ✅ 轻微改善（FN -1） | 依赖 `browser_file_access` 事件，覆盖有限 |
| **完成事件密集采样** | ❌ 完全无效 | 完成事件不存在于原始日志中 |
| **VLM Prompt 优化** | ⚠️ 难以评估 | 无法单独测试，且受采样限制 |

### 核心瓶颈

1. **日志信号不足** ⭐⭐⭐⭐⭐
   - 没有 `upload_complete`、`send_message` 等完成事件
   - 只有通用的 `browser_file_access`、`clipboard_text`
   - 无法从日志准确定位完成时刻

2. **完成证据难以捕捉** ⭐⭐⭐⭐
   - Toast 通知显示时间短（1-3 秒）
   - 成功提示可能被遮挡或不存在
   - 当前采样间隔（4-6 秒）容易错过

3. **Ground Truth 质量存疑** ⭐⭐⭐⭐⭐
   - 很多 FN 案例的 VLM 判断非常合理
   - 可能 30-50% 的 FN 是标注错误
   - 需要人工重新审查

### 下一步最优路径

**立即行动**: 
1. ✅ 启用帧调试，重新测试 10 个典型 FN 案例
2. ✅ 人工审查帧图片，验证 Ground Truth 是否准确
3. ✅ 如果发现大量标注错误，停止优化模型，转而修正数据集

**后续探索**:
- 如果 Ground Truth 准确 → 尝试混合决策策略（日志 + VLM）
- 如果采样密度是瓶颈 → 考虑成本与收益，是否值得 15 倍成本换取 10-20% 的 Recall 提升
- 如果完成证据本质上不可见 → 接受当前的 Recall 上限（~70%），或者改进数据采集方式（添加应用内埋点）
