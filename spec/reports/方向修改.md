## 问题的本质

### 当前方法：判断"是否完成" ❌

 **VLM 需要回答** : "文件是否**真的发送成功**了？"

 **需要的证据** :

* ✅ "发送成功" Toast（1-2 秒）
* ✅ "已发送"邮件列表
* ✅ 远程文件列表中出现文件
* ✅ 聊天历史中显示消息

 **困难** :

* ⚠️ 这些证据显示时间短、容易错过
* ⚠️ 很多应用没有明确的成功提示
* ⚠️ 日志中也没有完成事件

### 新方法：判断"是否有危险行为" ✅

 **VLM 需要回答** : "用户是否 **进行了危险操作** ？"

 **需要的证据** :

* ✅ 敏感文件被**拖拽到**邮件附件区（5-10 秒动作）
* ✅ 敏感内容被**粘贴到** AI 聊天框（可见输入框内容）
* ✅ 敏感文件出现在 **文件选择器** ，目标是网页上传框（持续 10-30 秒）
* ✅ **上传进度条**出现（持续 5-60 秒）
* ✅ 邮件 **撰写窗口有附件** （持续到发送前）

 **优势** :

* ✅ 这些都是 **过程证据** ，持续时间长（5-60 秒）
* ✅ 比完成提示（1-3 秒）**容易采样到 10-30 倍**
* ✅ 不需要看到"成功"提示，看到**尝试**就算

## 为什么这个方向更合理

### 1. **符合安全需求** ⭐⭐⭐⭐⭐

从企业 DLP（数据泄露防护）的角度：

| 场景                                           | 当前判断        | 新判断         | 哪个更合理？ |
| ---------------------------------------------- | --------------- | -------------- | ------------ |
| 用户将敏感文件附加到邮件，但关闭前未发送       | TN/FN（未完成） | TP（危险行为） | ✅ 新判断    |
| 用户复制敏感内容到 AI 聊天框，但关闭前未点发送 | TN/FN（未完成） | TP（危险行为） | ✅ 新判断    |
| 上传进度条到 90%，用户取消了                   | TN/FN（未完成） | TP（危险行为） | ✅ 新判断    |
| 敏感文件选择后，网络突然断了，上传失败         | TN/FN（未完成） | TP（危险行为） | ✅ 新判断    |

 **安全团队的真实需求** : "告诉我谁**试图**泄露数据"，而不仅仅是"谁成功了"。

### 2. **检测更容易** ⭐⭐⭐⭐⭐

| 证据类型           | 持续时间 | 采样捕获概率    | 示例                             |
| ------------------ | -------- | --------------- | -------------------------------- |
| **完成证据** | 1-3 秒   | 33%（5秒间隔）  | "发送成功" Toast                 |
| **过程证据** | 5-60 秒  | 95%+（5秒间隔） | 文件附加、输入框内容、上传进度条 |

 **采样间隔 5 秒的情况下** :

* 1 秒的 Toast → 只有 20% 概率被采样到
* 30 秒的附件准备 → 100% 会被采样到（至少 6 帧）

### 3. **VLM 判断更准确** ⭐⭐⭐⭐

| 问题                                        | 难度   | VLM 准确率（估计） |
| ------------------------------------------- | ------ | ------------------ |
| "这个文件是否**真的发送成功**了？"    | 极难   | 60-70%             |
| "用户是否**试图将文件附加到邮件** ？" | 简单   | 90%+               |
| "聊天框中是否**有敏感内容** ？"       | 简单   | 95%+               |
| "是否有**上传进度条** ？"             | 极简单 | 99%+               |

### 4. **Ground Truth 重新定义** ⭐⭐⭐⭐⭐

 **当前标注** （基于完成）:

```json
{
  "case": "1-email-163email-2",
  "expected": true,  // 表示"已成功发送"
  "leak_time": "12:14:01-02"  // 发送完成的时刻
}
```

 **问题** : 标注者如何知道"真的发送成功了"？

* 可能只是看到了"点击发送按钮"
* 可能网络断了、发送失败了
* 可能用户最后取消了

 **新标注** （基于危险行为）:

```json
{
  "case": "1-email-163email-2",
  "expected": true,  // 表示"有危险操作"
  "risk_behavior": "attach_sensitive_file_to_external_email",
  "risk_time_range": "12:13:30-12:14:30",  // 危险行为持续的时间段
  "risk_level": "high"  // attempted | in_progress | completed
}
```

 **优势** :

* ✅ 标注更容易（看到附加动作就可以标注）
* ✅ 标注更准确（不需要猜测是否"真的成功"）
* ✅ 时间范围更宽（30-60 秒，而不是 1-2 秒）

## 具体实施方案

### 修改 VLM Prompt

 **当前 Prompt（基于完成）** :

```
判断敏感数据是否真的泄露到外部？
- completed: 有明确完成证据（发送成功提示、已发送列表）
- in_progress: 传输中，但未完成
- selected_or_attached: 仅准备，未传输
```

 **新 Prompt（基于危险行为）** :

```
判断是否存在敏感数据泄露的危险行为？

危险行为包括（任一即为 positive）:
1. **内容暴露** (content_exposed):
   - 敏感文件内容在外部应用的输入框/编辑区可见
   - 敏感文本粘贴到 AI 聊天框、邮件正文、IM 消息框
   - 敏感文件在外部服务的预览窗口打开
   
2. **传输准备** (transfer_prepared):
   - 敏感文件附加到邮件附件区
   - 敏感文件选择器指向外部服务（网页上传框、云盘客户端）
   - 敏感文件拖拽到外部应用窗口
   
3. **传输进行** (transfer_in_progress):
   - 上传/发送进度条可见
   - 网络传输指示器（"正在发送..."、"Uploading..."）
   - 文件在外部服务的传输列表中（"传输中"状态）
   
4. **传输完成** (transfer_completed):
   - 成功提示（Toast、横幅）
   - 已发送列表中出现
   - 远程文件列表中出现

判断标准:
- 如果存在 1、2、3、4 中的任一行为 → risky_behavior: true
- 仅本地查看、本地编辑 → risky_behavior: false
- 不需要确认"是否成功"，只要"有尝试"即可
```

### 修改判断逻辑

 **当前逻辑** :

```python
if risk_level == "completed":
    positive = True
elif risk_level == "in_progress":
    positive = False  # 保守：未完成算 negative
elif risk_level == "selected_or_attached":
    positive = False
```

 **新逻辑** :

```python
if risky_behavior == True:
    positive = True  # 任何危险行为都算 positive
else:
    positive = False

# 可选：根据严重程度分级
severity = {
    "content_exposed": "critical",      # 内容已暴露
    "transfer_in_progress": "high",     # 传输中
    "transfer_completed": "high",       # 已完成
    "transfer_prepared": "medium",      # 准备阶段
}
```

### Ground Truth 重新标注（或重新解释）

 **选项 1: 重新标注** （工作量大）

* 人工重新审查所有案例
* 标注"危险行为时间范围"（而非"完成时刻"）

 **选项 2: 重新解释现有标注** （工作量小）

* `expected: true` = 有危险行为（包括尝试、进行、完成）
* `leak_time` = 危险行为的时间范围（而非精确完成时刻）

我建议 **选项 2** ，因为：

* 现有标注的 `leak_time` 可能本来就是"用户操作的时间段"
* 只需要在代码中重新解释，不需要重新标注
