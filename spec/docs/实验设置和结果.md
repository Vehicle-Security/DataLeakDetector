### figure6 不同 Stage 的本地关键帧筛选效果

> 在不同类型的泄露场景中，ScreenGuard 的全局视觉去重能够将日志窗口产生的候选关键帧减少多少？

实现边界：

- `raw_all` 是各日志分析窗口经动作状态抽帧和视觉变化抽帧后产生的全部候选帧。
- `raw` 是 `raw_all` 经跨窗口全局视觉去重后保留的关键帧。当前不使用 OCR 进行帧筛选或文本语义去重。
- 当前没有实现独立的 `raw -> VLM source frames` 缩减阶段，因此本实验只统计已实现的 `raw_all -> raw` 链路，不将网格拼图数量计入关键帧筛选效果。
- 项目输入是已录制的 MP4 和终端监控日志，不实现屏幕录制器，因此不统计“每日录屏存储量”。

实验流程：

- 使用 `artifacts/full_release_grid4x1_20260810_010848/vision_precompute` 中 326 个 case 的完整关键帧制品。
- 按 case 路径的顶层 Stage 分组，累加各 session `artifact_manifest.json` 中的 `keyframes_raw_all_files` 和 `keyframes_raw_files`。
- 去重帧数定义为 `raw_all - raw`，去重率定义为 `1 - raw / raw_all`。关键帧预计算发生在 VLM 调用之前，该统计不受 VLM 模型版本影响。

| Stage | Cases | `raw_all` candidates | Deduplicated `raw` | Removed frames | Reduction rate |
| ----- | ----: | -------------------: | -----------------: | -------------: | -------------: |
| stage0 |    40 |                  737 |                559 |            178 |         24.15% |
| stage1 |   182 |                3,574 |              3,033 |            541 |         15.14% |
| stage2 |    59 |                1,227 |                999 |            228 |         18.58% |
| stage4 |    30 |                1,097 |                949 |            148 |         13.49% |
| stage5 |    15 |                  410 |                347 |             63 |         15.37% |
| **Total** | **326** | **7,045** | **5,887** | **1,158** | **16.44%** |

全量数据中，本地全局视觉去重将 7,045 张候选帧减少为 5,887 张关键帧，总体减少 1,158 张（16.44%）。stage0 的缩减率最高（24.15%），stage4 最低（13.49%），说明不同场景中候选帧的视觉重复程度存在差异。

### figure7 不同 VLM 请求并发度下的端到端分析性能

> 在单个 Token Plan endpoint 上，调度器的并发度如何影响批次吞吐、case 延迟、排队时间和请求成功率？

实现边界：

- 当前 `build_vlm_clients()` 只保留第一个有效 endpoint，因此该实验测量的是单 endpoint 上的窗口级并发，不是多 Key 轮询或自建模型服务器的内部吞吐。
- `DLD_VLM_WORKERS` 控制共享请求队列的并发度及单 endpoint 并发槽位；Release 模式的 `--case-workers` 控制同时产生请求的 case 数。
- 现有制品记录 case 端到端耗时和批次排队时间，没有单独记录每次 HTTP 请求的服务时间。因此本表的 P95 必须标注为 **P95 case latency**，不写成服务端单请求 P95。

实验流程：

- 固定同一份 case 列表、`qwen3.7-plus`、4×1 网格和单个 Token Plan endpoint，复用 `vision_precompute` 结果，避免视频解码差异污染 VLM 并发实验。
- 依次测试并发度 1 / 2 / 3 / 4；每组同时设置 `--case-workers=N` 和 `--vlm-workers=N`，启用 `--vlm-fast-dispatch`。
- 每个并发度独立运行 3 次，报告中位数；任何超时、429、5xx 或断连都计入失败率，不丢弃失败样本。
- 批次吞吐量定义为 `completed VLM batches / wall-clock seconds`；P95 case latency 由 `release_progress.json` 中每个 case 的 `seconds` 计算；排队时间和批次成功率来自 `vlm_dispatch` 统计。

最佳并发度以“批次成功率不下降且吞吐最高”为主准则，P95 case latency 和排队时间作为约束，不仅根据吞吐量单独判定。现有 `qwen3.7-plus` 全量运行在并发度 20 下完成 418/418 个 VLM 批次，总墙钟时间为 2,194.061 s，对应 0.191 batches/s；该点只用于校验指标口径，不用于推断 1–4 范围内的最佳并发度。
