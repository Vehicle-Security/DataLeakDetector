# DataLeakDetector Overview

## Summary

本次重构的目标不是把旧仓库原样搬运到新仓库，而是为 `DataLeakDetector` 建立一套可协作、可复现、可解释、可继续开发的模块 2/3 新基线，同时保持当前端到端主链路可跑通。

结合当前仓库状态、已有回归测试和 10-2 样例跑通结果，可以推断本轮重构意图如下：

- 保留模块 1 现有能力和接口，不在本轮重写其核心逻辑。
- 优先修复模块 2 和模块 3 的结构混乱、职责耦合、重复告警、映射链不稳、配置脏和协作不可维护的问题。
- 交付物必须不仅能跑，而且要让后续同学能快速理解系统结构、定位入口并继续迭代。
- 模块 4 本轮作为稳定下游依赖使用，不改动其核心推理逻辑。

## Project Goal

项目目标是构建一条基于日志、录屏视频、VLM 和 Datalog 的端到端数据泄露检测流水线，用于发现敏感文件被隐蔽转换、上传或外发的行为，并输出可追溯的风险证据报告。

当前系统默认关注以下问题：

- 敏感文件是否被打开、转换、重命名、复制或衍生出新文件。
- 用户是否通过黑名单应用、网页平台或可疑上传动作进行外发。
- 是否能够将日志中的文件行为、视频中的界面行为和最终外发证据连接成一条完整泄露路径。

## E2E Data Flow

### Inputs

- 日志文件：通过 `--log` 传入。
- 录屏文件：通过 `--video` 传入。

### Entry

- 入口命令保持不变：

```powershell
python .\main\main.py --log <log.json> --video <recording.mp4>
```

- `main/main.py` 负责将执行转发到仓库根目录的 `run_e2e.py`。

### Pipeline

1. `run_e2e.py` 加载日志和视频路径，并创建本次运行所需的临时 `INDEX.md`。
2. 模块 3 `RiskHunter` 作为总控模块启动完整分析流程。
3. 模块 3 内部调用模块 2 `FileTracker` 对单个敏感事件做深入分析。
4. 模块 2 内部调用模块 1 `FrameAnalyzer`，在指定时间窗内分析视频帧并提取事件级行为结果。
5. 模块 3 根据模块 2 和模块 1 的结果生成敏感操作记录、上传事件、告警事件和文件映射。
6. 模块 4 `ThreatDetector` 消费日志和模块 3 结果，注入 Datalog 事实并推理泄露路径。
7. 流水线最终输出根目录 `output/full_evidence_<timestamp>.json`。

## Module Boundaries

### Module 1: FrameAnalyzer

- 负责视频帧检索、OCR/VLM 分析和事件级行为识别。
- 输入是时间窗和目标文件关键词。
- 输出是事件列表及其行为语义，不直接维护 worklist、文件映射或告警。

### Module 2: FileTracker

- 围绕单个敏感文件事件执行隐藏操作识别、派生文件生成、文件路径解析和文件映射维护。
- 输入是一个敏感文件相关事件和对应分析上下文。
- 输出是隐藏操作、派生事件、路径映射和分析状态，不承担最终上传判定和告警分级。

### Module 3: RiskHunter

- 负责初始化 `WorklistManager`、构建初始 worklist、调度模块 2、判定上传与告警、汇总统计和导出文件映射。
- 模块 3 是本轮重构的总控核心，也是后续协作最需要稳定的模块边界。

### Module 4: ThreatDetector

- 负责将日志与模块 3 结果转换为 Datalog 事实并执行推理。
- 输出完整泄露路径与证据链。
- 本轮只要求模块 2/3 对其接口保持兼容，不改动其核心逻辑。

## Confirmed Problems

当前仓库已确认存在以下问题：

- 模块 2 和模块 3 职责交叉，状态字段较多，内部耦合偏强。
- `upload_detection_config.py` 中存在大量硬编码样例数据，样例配置与真实配置混杂。
- 同一上传事实可能扩张成多条重复告警，结果层可读性较差。
- 文件映射在部分场景下仍需依赖日志兜底推断，稳定性不够。
- 输出中的中文字段存在编码可读性问题，影响报告查看和对外展示。
- 新仓库虽然已能在 10-2 样例上跑通，但协作入口、文档和重构边界仍需正式收口。

## Refactor Goals

本轮重构目标如下：

- 稳定模块 2/3 的输入输出契约，减少后续开发时的隐式耦合。
- 让 worklist、文件映射、操作记录和告警去重规则可说明、可测试、可维护。
- 保持当前 CLI 用法不变，保持端到端主链路可跑通。
- 保持报告主结构不变，尤其是 `summary`、`module3_risk_hunter` 和 `module4_threat_detector`。
- 将重构重点放在模块 2/3 内部结构与结果质量收敛，而不是大规模更换整体技术方案。

### Default Refactor Principles

- 保持 `run_e2e.py` 的主流程职责不变。
- 先保证“还能跑通”，再收敛模块 2/3 内部结构和结果质量。
- 优先保留已有回归测试覆盖到的行为语义。
- 所有会影响下游模块 4 的结构性改动必须以兼容为前提。

## Non-goals

本轮不做以下事项：

- 不重做模块 1 的 VLM prompt 和视觉分析主逻辑。
- 不更换模块 4 的 Datalog 推理方案。
- 不试图一次性解决全部数据质量问题，只针对当前基线样例和已暴露的结构性问题收敛结果。
- （不在本轮把所有硬编码配置彻底产品化。）

## Acceptance Baseline

### Regression Tests

必须通过以下回归测试：

```powershell
python -m unittest tests.test_e2e_regressions -v
```

当前重点保护的行为包括：

- 统计字段与 `processed_count` 同步。
- 多输出隐藏操作能够正确拆分。
- 已知派生敏感文件不会重复入队。
- Datalog 推理不会因为映射循环而无限扩张。
- 模块 3 结果可以为模块 4 补足可连接的泄露事实。

### E2E Validation

必须满足以下端到端验收条件：

- 使用 10-2 样例运行新仓库入口。
- 模块 3 和模块 4 都成功加载并执行。
- 根目录 `output/` 下生成新的 `full_evidence_*.json`。
- 报告中的 `summary.module3_events_processed`、`summary.module3_upload_events`、`summary.module4_leak_paths` 不为空。
- 至少检测到一次与 QQ 邮箱上传相关的风险结果。

## Assumptions

- “重写 2/3 模块”默认解释为重写模块 2 `FileTracker` 和模块 3 `RiskHunter`，不是重写整个项目三分之二。
- 模块 1 当前质量可接受，本轮只依赖其接口，不重写其核心逻辑。
- 模块 4 当前边界较稳定，本轮不改其推理核心，只要求接口兼容。
- 当前 10-2 跑通结果是本轮重构的验收基线。
- 如果后续导师明确要求配置外部化，则将配置重构升级为正式交付项。
- （如果后续导师明确要求“报告可读性”必须本轮交付，则将中文编码修复升级为正式交付项。）
